# Workbench

Workbench is a workspace-oriented chat application for running an AI coding agent against local project directories. Users create workspaces and sessions, send prompts, and see assistant replies and tool-call inputs in the session transcript. Conversations and tool calls are stored in MongoDB.

The repository is a Bun workspaces monorepo orchestrated with Turborepo. The frontend and backend are separate processes and should be started in separate terminals.

## Features

- Create workspaces from filesystem paths.
- Group multiple chat sessions under each workspace.
- Load workspace sessions and their conversation history when the WebSocket client connects.
- Send user prompts to the Claude Agent SDK with the workspace path as its working directory.
- Show and persist SDK tool calls, including tool names and inputs.
- Require explicit user approval before the agent can use the `Edit` tool; allow or reject from the chat UI.
- Persist user and assistant messages in MongoDB.
- Return a demo assistant reply when an SDK request fails or completes without a successful result. The demo reply is not generated by an AI model.

- Bun 1.4 or newer

## Requirements

- Bun 1.4 or newer. The repository's `devEngines` currently specifies Bun 1.4.0.
- MongoDB, local or hosted.
- Agent SDK authentication for real Claude responses. Configure authentication using a method supported by the installed Claude Agent SDK. Without it, the backend falls back to a fixed demo response; the fallback does not execute tools.

## Setup

Install dependencies from the repository root:

```sh
bun install
```

Create `apps/backend/.env` with a MongoDB connection string:

```dotenv
DB_URL=mongodb://127.0.0.1:27017/workbench
```

For a hosted database, use its connection URI as `DB_URL`. Keep credentials private and do not commit them.

For real agent responses, configure the Claude Agent SDK's required authentication in the environment used by the backend. The application itself does not provide an authentication flow.

## Run Locally

Start the backend from the repository root in one terminal:

```sh
cd apps/backend
bun index.ts
```

The backend connects to MongoDB and listens for WebSocket connections on port `3000`.

Start the frontend from the repository root in a second terminal:

```sh
cd apps/frontend
bun run dev
```

Open [http://localhost:3001](http://localhost:3001). The frontend connects to `ws://localhost:3000`.

The root `bun run dev` command invokes `turbo run dev`. At present, the backend package does not define a `dev` script, so start the backend separately as shown above. If either port is already in use, stop the existing process or update the corresponding server/client port configuration.

## Message Flow

The browser and backend communicate with JSON messages over WebSockets. Incoming payloads are validated with schemas from `packages/commons`.

1. On connection, the backend loads workspaces and their sessions and sends an `init` event.
2. The frontend sends `create-workspace` or `create-session` requests. The backend saves them and replies with the created resource ID.
3. For `add-message`, the backend saves the user message and queries the agent with the workspace directory as `cwd`.
4. Read-only `Read` and `Glob` calls are allowed. Before an `Edit`, the backend sends an `approval-request` event and waits for the user's decision; the decision is saved with the tool call.
5. On successful agent completion, the backend saves and sends the assistant result. If the SDK fails or produces no successful result, it sends and saves a demo response instead.

Important event shapes include:

```ts
// Browser to backend
{ type: "create-workspace", payload: { path: string } }
{ type: "create-session", payload: { workspaceId: string } }
{ type: "add-message", payload: { sessionId: string, message: string } }
{ type: "tool-approval-response", payload: { requestId: string, approved: boolean } }

// Backend to browser
{ type: "init", workspaces: Workspace[] }
{ type: "assistant-message", payload: { type: "result", message: string } }
{ type: "tool-call", payload: { sessionId: string, name: string, input: unknown } }
{ type: "approval-request", payload: { requestId: string, sessionId: string, toolName: string, input: unknown, title: string } }
{ type: "tool-approval-result", payload: { requestId: string, approved: boolean } }
```

The shared event and conversation types live in `packages/commons/outgoing.ts`; incoming request schemas live in `packages/commons/incoming.ts`.

## Data Model

- **Workspace:** filesystem `path` and display `name`.
- **Session:** reference to a workspace, a `conversation` array, and an optional `anthropicSessionId` used to resume agent conversations.
- **Conversation entry:** `role` (`user`, `assistant`, or `tool`) and a `payload`. Tool entries include the tool name and input; edit entries also record the approval state; assistant entries include the result text.

Mongoose models are defined in `packages/db/index.ts`. The workspace path is used as the agent's working directory. Use only directories you trust: the agent is configured with `Read`, `Glob`, and `Edit`; edits require approval, while other tools are denied.

## Build and Typecheck

Build the frontend:

```sh
cd apps/frontend
bun run build
```

Typecheck the frontend and backend from the repository root:

```sh
bun x tsc -p apps/frontend/tsconfig.json --noEmit
bun x tsc -p apps/backend/tsconfig.json --noEmit
```

There is currently no automated test script configured in the root package scripts.

## Current Limitations

- The frontend WebSocket URL and server ports are configured for local development (`localhost:3000` and `3001`).
- There is no user authentication or authorization layer on the WebSocket server. Do not expose it to untrusted networks as-is.
- Real agent execution needs valid SDK authentication. The demo fallback only confirms that the message flow works; it does not perform coding tasks.
- Tool calls and assistant replies are persisted, but the application is an early-stage prototype rather than a production-hardened agent environment.
